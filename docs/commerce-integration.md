# Nyxi commerce integration boundary

The website is static. The Nyxi detail view and cart are a frontend catalogue only; the cart stores product slugs and quantities in the visitor's browser. It does not submit an order, collect customer or card details, charge a payment method, or grant a download.

## Product setup

Product source data lives in `works/products/*.md`; `assets/products/catalog.js` is generated by `py build_catalogs.py` and should not be edited by hand. Copy `templates/product-template.md` to `works/products/<name>.md`, fill the product fields, and put public preview images under `assets/img/products/<slug>/`. The build validates image paths and writes the data consumed by the current product detail view and cart. To remove a product, remove its Markdown source and rebuild; stale cart entries for removed slugs are discarded.

Nyxi's `price` and `salePrice` are deliberately `null` because no price or currency was supplied. When pricing is decided, set either field to an object such as `{ amount: 12.50, currency: 'EUR' }` using the actual price and ISO currency. The cart formats unit prices, line subtotals, and the total from that data. Do not trust a price sent by the browser as the amount to charge.

Promotional WebP previews are public website assets in `assets/products/nyxi/`. The product ZIP is not in the repository. Keep the original archive outside the website's document root, or place it in a private object-storage bucket with public access disabled. Never put the package ZIP in `assets/` or expose a public URL to it.

## Required backend before sales or delivery

1. Add a server endpoint such as `POST /api/checkout-sessions`. It should accept product identifiers and quantities only, look up current prices and availability server-side, create a checkout session with a payment provider, and return the provider's hosted checkout URL. The browser should never handle card details or provider secrets.
2. Add a provider webhook endpoint. Verify its signature using a server-side secret, retrieve/verify the payment with the provider, and only then mark the order paid. A browser redirect or a client-supplied success flag must never fulfill an order.
3. Keep order records and product-to-private-file mappings on the server. Store the ZIP in private storage, not the static site.
4. After a verified payment, authorize the purchased product for that order and issue a short-lived signed download URL (or stream the file through an authenticated endpoint). Check the paid order and entitlement on every download request; do not reveal the storage key or permanent file URL.
5. Configure server secrets in the hosting provider's secret manager and define retention, refund, and failed-payment handling before launch.

The current checkout button stays disabled until this backend and provider are implemented and tested. No payment provider, endpoint, price, or download URL is configured in this project.
